# Глибокі ціни: надбавки й знижки

    pnpm install
    pnpm --filter @dt/contracts build
    ./scripts/setup-neon.sh
    pnpm -r typecheck && pnpm -r test
    git add -A && git commit -m "Ціни правилами: надбавки за розмір, тканину, колір; опт і акції" && git push

Міграція `20260826070000_price_rules` створює дві таблиці й додає
`Order.discountName`. Даних не змінює: без жодного правила ціна рахується
рівно так, як рахувалася.

## Як це влаштовано

Ціна складається в чотири такти, і порядок зафіксовано:

    ціна виробу  = база + Σ надбавок        (або ручна ціна варіанта)
    ціна одиниці = ціна виробу + друк
    рядок        = ціна одиниці × кількість
    до сплати    = рядок − одна найкраща знижка

**Надбавки складаються, знижки — ні.** Це різні речі. Надбавка каже, чим цей
виріб відрізняється від базового: 2XL дорожчий, начіс дорожчий, і обидві
відмінності можуть бути одночасно. Знижка — це домовленість із покупцем, а
домовленість діє одна. Якби знижки складалися, дві акції по 60 % віддавали б
товар безкоштовно, і помітили б це тільки в звіті.

Відсоткові надбавки рахуються **від базової ціни**, а не одна від одної. Тому
результат не залежить від того, яке правило створили першим.

## Чому правила, а не ціна в кожному варіанті

Варіантів у нас тисячі: 7 виробів × 4 тканини × 23 кольори × 8 розмірів.
Проставити ціну в кожному — це таблиця, яку ніхто ніколи не перевірить.
Правил натомість одиниці, і кожне читається вголос: «2XL +50 ₴».

Ручна ціна варіанта (`Variant.priceOverrideMinor`) лишилася й має вищий
пріоритет: правила описують систему, override — свідомий виняток із неї.

## Що ловить база, а не код

  · надбавка з ціллю «тканина», але без тканини — CHECK;
  · два однакові правила (вони б тихо подвоїли ціну) — унікальний індекс
    по виразу з COALESCE, бо звичайний складений тут не працює: у Postgres
    NULL не дорівнює NULL;
  · відʼємна знижка, знижка понад 100 %, перевернуте вікно дат — CHECK;
  · знижка одночасно на виріб і на колекцію — CHECK.

## Де рахується ціна

Одна чиста функція, три місця виклику: вітрина, каса, калькулятор в адмінці.
Сервер віддає `variant.priceMinor` уже порахованим — браузер не складає ціну
сам, інакше рано чи пізно розійдеться з касою.

## Калькулятор

`/admin/tsiny` → вкладка «Калькулятор». Показує розкладку по рядках: база,
кожна надбавка окремо, друк, кількість, знижка, до сплати. Рахує той самий
код, що й каса, — тому йому можна вірити.
