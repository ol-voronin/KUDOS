# Doggie Tale — робочий каркас

Монорепозиторій магазину: Next.js 14 (App Router) + NestJS 10 + PostgreSQL + Redis,
строгий TypeScript, спільні контракти на zod.

Це **каркас для роботи**, а не готовий магазин. Доменна модель, ціноутворення,
правила доступності й контракт API — реальні й покриті тестами. Сторінки
каталогу — заглушки з чіткими швами, позначеними `TODO(step 2)`.

---

## Швидкий старт

```bash
cp .env.example .env
# згенерувати секрети:
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

pnpm install
pnpm run build:contracts          # @dt/contracts має бути зібраний першим
docker compose up -d postgres redis
pnpm --filter @dt/api prisma generate
pnpm --filter @dt/api prisma migrate dev --name init
pnpm --filter @dt/api prisma db seed

pnpm --filter @dt/api dev         # :4000, Swagger на /api/docs
pnpm --filter @dt/web dev         # :3000
```

**Перевірка:** `pnpm run typecheck && pnpm -r test`

## Структура

```
packages/contracts   zod-схеми + типи. Єдине джерело правди для API і фронта.
apps/api             NestJS. Домен → застосунок → інфраструктура.
  prisma/schema      п'ятирівнева модель товару
  src/pricing        чисті функції: ціна, доступність, розрахунок кошика
  src/catalog        читання каталогу
  src/custom-requests воронка «принт з 0»
  src/leads        заявка -> Telegram
apps/web             Next.js. Feature-based, не page-based.
  src/features/catalog/variant-selection.ts   логіка вибору, без React
```

Контракти — окремий пакет навмисно. Два паралельні описи одного тіла запиту
розходяться протягом спринту; так розходження неможливе фізично.

## Чотири рішення, які варто зрозуміти перед тим, як писати код

### 1. Гроші — цілі копійки, ніколи не float

`Minor` — брендований `number`. `minor(1.5)` кидає виняток. Форматування в
`1 600 ₴` відбувається один раз, на краю, у `formatUAH`. Причина не
теоретична: дрейф в одну копійку на позицію стає проблемою звірки тієї миті,
коли на цифри подивиться друга людина.

### 2. Доступність варіанта — найважливіше поле в каталозі

```ts
enum VariantAvailability { IN_STOCK, MADE_TO_ORDER, UNAVAILABLE }
```

Власне виробництво гарантує рівно один колір у наявності — чорний. Решта —
«пошиємо, але доставка з іншого міста займе довше». `MADE_TO_ORDER` **вимагає**
`leadTimeDays`: це перевіряє і zod, і CHECK-констрейнт у БД, і `blockReasonFor`.

Продавати з кошика те, для чого немає обіцяного строку — це скасовані
замовлення. Модель даних робить це неможливим.

### 3. Заявки йдуть у Telegram

`POST /api/v1/leads` з `{ name, phone, message?, source? }` надсилає повідомлення
в бот. Все.

```bash
curl -X POST localhost:4000/api/v1/leads \
  -H 'content-type: application/json' \
  -d '{"name":"Оля","phone":"+380671234567","message":"худі з коргі"}'
```

Налаштування — два рядки в `.env`:

```
TELEGRAM_BOT_TOKEN=   # @BotFather -> /newbot
TELEGRAM_CHAT_ID=     # https://api.telegram.org/bot<ТОКЕН>/getUpdates -> chat.id
```

Перевірити бота, не запускаючи API:

```bash
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... node apps/api/scripts/send-test.mjs
```

Ім'я екранується — `Аня <3` інакше ламає повідомлення. Токен у логи не потрапляє.
Ліміт 20 заявок на годину з IP.

### 4. «Принт з 0» — це не Order

Окремий агрегат `CustomRequest` з власним життєвим циклом
(`SUBMITTED → QUOTED → DEPOSIT_PAID → IN_DESIGN → …`). 16-годинний цикл дизайну
— це проєкт, а не покупка. Заявка створюється **без ціни**: неоцінений бриф не
має суми, і вигадувати її до скоупінгу — це продати 16-годинну роботу за ціною
двогодинної.

### 5. Постачальник — властивість виробу, а не розділ сайту

Ніхто не шукає «футболку Native Spirit». Лінійка живе в моделі даних і на
картці товару, у навігації її немає — там колекція й порода.

## Модель товару

```
Лінійка → Виріб (тип + крій) → Тканина → Колір → Розмір
```

П'ять рівнів, а не чотири. Зайвий — **тканина**: світшот власного виробництва
шиється з петлі або з начісу, і в кожної своя палітра.

Ще дві речі, що не зводяться до спільного компонента:

- **Розміри належать виробу.** У асортименті дев'ять різних схем
  (`XS–3XL`, `XS/S–XL/2XL`, `S/M–L/XL`, `XXS–XXL`, `98–152`, `116–152`…).
  Універсального селектора не буде.
- **Заміри — рядки, не колонки.** Футболки власного виробництва: ширина +
  довжина. Native Spirit: + рукав. Джогери: талія + стегна + довжина.

Правило «Портрети — тільки оверсайз» живе в `PrintGarmentRule` як дані, а не як
виняток у чиїйсь голові.

---

## Ціноутворення

```
позиція = ціна виробу + ціна друку
```

Ціна друку — за **розміром принта** (MINI 500 ₴ / MEDIUM 600 ₴ / MAXI 700 ₴),
не за методом: DTF і DTG працюють на обох лінійках.

Знижка 150 ₴ за готовий макет застосовується **тільки** у воронці «з 0» і не
може загнати дизайн-рядок у мінус (`quoteCustom` клампить).

`designPriceForHours(hours, rate)` існує, щоб число було в адмінці, а не в
розмові: при 16 годинах на замовлення кожні 100 ₴/год додають 1600 ₴ до ціни.

Ціни в замовленні — **знімок**. Перерахунок старого замовлення за поточними
цінами це баг, тому `OrderItem` зберігає `garmentPriceMinor`, `printPriceMinor`
і `lineTotalMinor` окремо.

## Тести

28 тестів, усі зелені.

| Пакет | Що покрито |
|---|---|
| `@dt/contracts` | арифметика грошей, межі, відмова від дробових копійок |
| `@dt/api` | ціна, правила блокування, межа lead time, розрахунок кошика, квоти |
| `@dt/web` | вибір кольору й розміру, три стани доступності |
| `@dt/api` | формат заявки в Telegram, екранування HTML |

Межі перевіряються явно: `leadTimeDays === MAX` проходить, `MAX + 1` — ні.
`totalCart` кидає виняток на непридатній позиції замість того, щоб мовчки її
викинути — кошик, який тихо втрачає товар, це звернення в підтримку.

Не покрито поки: інтеграційні тести з БД, E2E (замовлення, бриф),
контрактні тести. Каркас під них є.

## Security review

**Зроблено:**

- Кожен ендпоінт вважається публічно доступним. Глобальний `ThrottlerGuard`
  (120 req/min), бриф — окремо 5/год: неавтентифікований, приймає вільний
  текст, створює роботу для двох людей.
- `helmet`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`,
  `Permissions-Policy` на обох застосунках.
- CORS — тільки явний allowlist. Wildcard кидає виняток при старті.
- Валідація одна на всіх — zod із `@dt/contracts`, на вході й на виході.
- Секрети тільки з оточення; `main.ts` падає на старті, якщо `JWT_*` чи
  `DATABASE_URL` порожні або лишились `__replace_me__`.
- `correlationId` у кожному запиті, відповіді й рядку аудиту. Client-supplied
  id не приймається як є — валідується регуляркою, інакше генерується свій.
- Внутрішні помилки логуються зі стеком, клієнту йде загальне повідомлення.
- Логуються тільки ідентифікатори. Пароль, токен, платіжні дані, вміст брифу й
  контакти в логи не потрапляють.
- `artworkKey` (продакшн-макет) не виходить у публічний API.

**Треба зробити до продакшну:**

- Auth: JWT access/refresh, ротація refresh, RBAC для адмінки.
- Фото собак — приватний бакет, presigned upload, перевірка MIME й розміру,
  антивірус. Зараз у брифі приймаються тільки storage keys, не байти —
  ендпоінт завантаження ще не написаний.
- CSRF для cookie-based сесій.
- Ідемпотентність оформлення замовлення (ключ на рівні БД).
- Верифікація підпису вебхуків платіжки + захист від replay.
- Rate limiting у Redis, а не в пам'яті — інакше не працює на кількох інстансах.
- Політика конфіденційності має назвати, що ім'я й телефон ідуть у Telegram.

## Performance review

- Кожен запит вибирає явні поля. `include: { всё: true }` — це те, як сторінка
  товару перетворюється на сорок запитів; перевірка на N+1 починається саме тут.
- `listPrints` бере сторінку й лічильник в одній транзакції.
- Індекси під реальні шляхи: `Variant(garmentId, availability)`,
  `Print(isPublished)`, `PrintBreed(breedId)`, `Order(status, placedAt)`.
- Композитні унікальні ключі не дають дублів варіантів і розмірів.
- React Query зі `staleTime` 60 с на картці товару.

Не оптимізовано (свідомо, до перших цифр): кеш каталогу в Redis, ISR для
породних сторінок, `next/image`.

## Що перевірено, а що ні

Оточення, у якому це збиралось, не має доступу до `binaries.prisma.sh` (403),
тому Prisma CLI там не запускається взагалі — ні `generate`, ні `migrate`, ні
навіть `validate`. Перевірку зроблено в обхід CLI, офіційними пакетами.

**Перевірено:**

- **Схема валідна.** `@prisma/prisma-schema-wasm` того самого коміта
  (`605197351a3c…`), що й движок у `@prisma/engines-version` — це той самий
  парсер і валідатор, який використовує CLI. 21 модель, 11 енумів, помилок 0.
- **Код збігається зі схемою.** Кожне звернення `prisma.<модель>.<операція>`
  в `apps/api/src` і в сіді розібрано через TypeScript AST і звірено з DMMF:
  моделі, поля в `data` / `where` / `select`, вкладені `create` по звʼязках,
  і чи справді унікальні ті ключі, за якими робиться `upsert` і `findUnique`.
  Розбіжностей 0.
- **Фізична модель лягає на PostgreSQL 16.** DDL, згенерований із DMMF,
  застосовано на живій базі: 21 таблиця, 61 індекс, 22 зовнішні ключі,
  11 енумів, 1 CHECK. Помилок 0.
- **Правила поводяться так, як обіцяно.** На живій базі перевірено:
  `MADE_TO_ORDER` без `leadTimeDays` не вставляється; зі строком — вставляється;
  дубль варіанта по `(garment, fabric, colour, size)` не проходить; два ліди на
  один телефон дають одного клієнта, а `Lead.number` рахується сам; дубль
  клієнта по телефону не проходить; видалення виробу каскадом забирає варіанти.
- **40 тестів зелені**, збірка `@dt/contracts` чиста.

**Не перевірено — і чому:**

- **`prisma generate` не запускався.** Через це `tsc --noEmit` проходить, але
  **нічого не доводить про Prisma**: без генерації `@prisma/client` віддає
  110-рядковий заглушковий тип, у якому немає жодної моделі. Саме тому звірку
  коду зі схемою зроблено окремо, через DMMF, — і це та перевірка, яку
  `typecheck` тут зробити не міг.
- **Міграції не генерувались.** SQL, яким перевірялась фізична модель, зібрано
  власним скриптом із DMMF, а не движком міграцій, тож він **не є міграцією** і
  в репозиторій не потрапив. Справжню першу міграцію створює `migrate dev`.
- **Застосунки не піднімались.** Рантайм `PrismaClient` вимагає нативного
  движка, якого в тому оточенні немає.

## Найближчі кроки

Перше — одна команда локально, там, де є інтернет до `binaries.prisma.sh`:

```bash
cp .env.example .env          # заповнити TELEGRAM_* і JWT_*
ln -s ../../.env apps/api/.env         # Prisma CLI шукає .env поруч зі схемою
pnpm install
pnpm run build:contracts
docker compose up -d postgres          # redis поки не потрібен, його ніщо не використовує
pnpm --filter @dt/api prisma generate
pnpm --filter @dt/api run db:setup     # migrate dev + checks.sql + seed
pnpm run typecheck && pnpm -r test     # ось тепер typecheck справді щось значить
```

Символьне посилання обовʼязкове: скрипти `@dt/api` виконуються з `apps/api`, а
`.env` лежить у корені монорепо. Без нього Prisma не бачить `DATABASE_URL`.
`.env` у `.gitignore` за шаблоном без слеша, тож посилання в гіт не поїде.

`db:checks` накатує `prisma/checks.sql` — CHECK-констрейнт, який Prisma не
вміє описати в схемі. Він ідемпотентний, і його треба ганяти після кожної
міграції, інакше `migrate reset` тихо його знесе.
